# adding-neon-resource

## Overview

Net-new resources on terraform-plugin-framework land through a fixed ten-file shape, in a fixed order, against a fixed test surface. The openspec change is the source of truth for what gets built; code mirrors it.

## When to Use

- New `neon_*` resource requested for the first time.
- Porting an SDK v2 resource to framework.
- Adding a data source that mirrors a resource.

Not for: bug fixes in existing resources, refactors of CRUD, or schema additions to shipped resources (open a normal PR).

## Core Pattern

Ten files, in this order. Skip nothing.

1. **openspec change first.** Create `openspec/changes/add-neon-<name>/` with `proposal.md`, `design.md`, `tasks.md`, and `specs/neon-<name>/spec.md`. No code before proposal lands.
2. **`provider/resource_<name>.go`.** Interface asserts (`Resource`, `ResourceWithConfigure`, `ResourceWithImportState`, `ResourceWithModifyPlan`). Model struct with `tfsdk:` tags only on Framework-facing fields. `Metadata`, `Schema`, `Configure`, `Create`, `Read`, `Update`, `Delete`, `ImportState`, `ModifyPlan`. Wrap every API call in `projectReadiness.RetryFramework` (plain) or `projectReadiness.RetryWithFallbackFramework` (per-status-code fallbacks, e.g. 404 → `RemoveResource`).
3. **`provider/acc_<name>_test.go`.** Minimum four subtests: create + read, update-or-no-update (forced replace), import, out-of-band deletion. Use `newProviderFactories` (plural — see Quick Reference).
4. **Register in `provider/provider.go`.** Add `NewNeon<Name>Resource` to the `Resources(...)` slice, alphabetically placed (bucket, function, service_credential, then new).
5. **`examples/resources/neon_<name>/resource.tf`.** Hand-written; the doc template embeds it via `{{ tffile }}`. Match the schema's exact attribute names — no invented attributes.
6. **`templates/resources/<name>.md.tmpl`.** Header frontmatter + `{{ tffile ... }}` + `{{ .SchemaMarkdown }}` + Import block.
7. **`docs/resources/<name>.md`.** Generated by `make docu`. Do not hand-edit.
8. **`CHANGELOG.md`.** New minor version section above `[Unreleased]`. Note SDK bump if `go.mod` changed.
9. **Verify:** `go vet ./...`, `go build ./...`, `go test ./provider/... -short`, then `make testacc` with `TF_ACC=1` and `NEON_API_KEY`.
10. **PR.** Local commit on a feature branch; PR gated on user permission per AGENTS.md.

## Quick Reference

| Convention | Value |
|---|---|
| Framework types in model struct | `types.String`, `types.Bool`, `types.Int64`, `types.Map{StringType}`, `types.List{...}` |
| Internal helpers, SDK wrappers, FSM inputs | Go standard library types (`string`, `int`, `map[string]string`, `time.Time`) |
| Forced-replace helper | `stringChanged(a, b types.String) bool` from `provider/helper.go` |
| FSM entry | `projectReadiness.RetryFramework` / `RetryWithFallbackFramework` |
| Acceptance provider factory | `newProviderFactories` — the only factory in this fork (defined at `provider/provider.go:192`) |
| Composite ID | `<project_id>/<branch_id>/<name>` |
| Sensitive attributes | `Sensitive: true` on the schema + never logged via `tflog` |
| Nested blocks vs flat attrs | Prefer flat `StringAttribute` over `SingleNestedAttribute` when the block has only one field (e.g. `schedule = "* * * * *"` over `schedule { cron = ... }`). Use nested blocks only when 2+ fields are semantically grouped (e.g. `storage_object_created { bucket_name, prefix }`). |
| Test config helpers | One helper per file (e.g. `newProjectConfig(name)`, `newFunctionConfig(...)`) at file scope. Accepts only parameters that vary between test steps; hardcode constants like `region_id`, `org_id` in the helper body. |
| Test ID lookups | Inside `Check` blocks, read project_id, branch_id, and other composite IDs from `state.RootModule().Resources[...]`. The SDK client is for assertions, not for lookup of resources Terraform just created. |
| Test destructive ops | `PreConfig` callbacks that delete resources out-of-band keep their `client.Delete*` calls. They are the disappears-test pattern; the SDK is the only way to simulate out-of-band deletion. |
| Test sweeps | `t.Cleanup` SDK sweeps stay. They run after Terraform state is gone; only the SDK knows what was created. |

## Common Mistakes

- **Writing code before the openspec proposal.** Reverts cleanly only if caught in PR review; otherwise the openspec archive becomes inconsistent.
- **Mixing `types.String` and `string` in the model struct.** The model must be all Framework types so `req.Plan.Get`/`req.State.Get` work. Go-native `string`/`int`/`time.Time` belongs in helper structs, SDK wrappers, FSM callbacks, and `tflog` calls.
- **Reaching for `types.String` outside the model struct.** Framework types exist to bridge HCL into the model. Anywhere else — internal helpers, SDK wrappers, FSM inputs, log payloads — Go standard types are simpler and skip null-handling ceremony. Rule: if a value is not on the schema, do not wrap it in a Framework type.
- **Reading test fixtures from the SDK instead of from `*terraform.State`.** Inside a `Check` block, every assertion reads `state.RootModule().Resources["neon_<name>.this"].Primary.Attributes["<attr>"]`. Round-tripping through `client.ListProjects` to find a project we just created is the pattern this skill replaces. The `t.Cleanup` SDK sweep stays — Terraform state is gone by then.
- **Inlining `fmt.Sprintf` HCL configs instead of extracting helpers.** When a test step defines a config string with `fmt.Sprintf(`resource "neon_project" "this" { ... }`, projectName, ...)`, that string should live in a helper named `newProjectConfig`, `newBranchConfig`, `newFunctionConfig`, etc. at file scope. The helper accepts only the parameters that vary between test steps; constants like `region_id`, `org_id`, runtime versions, and other fixed values are hardcoded in the helper body. Rationalizations to refuse: "the test only uses the config once" (the helper takes the same line count and removes a future edit hazard when the resource schema changes), "the inline string is clearer" (the inline string is the same HCL, just surrounded by `fmt.Sprintf` plumbing), "I'd duplicate the HCL across helpers" (one helper per resource is the rule; the HCL does not appear in `func TestAcc*` bodies), "the existing tests have inline configs" (this rule supersedes the existing convention; convert inline configs as you touch each test file).
- **Forgetting ImportState or the import subtest.** Every framework resource has one. Test the `<project>/<branch>/<name>` composite form.
- **Forgetting the out-of-band deletion subtest.** Resource deleted in Neon without Terraform; next `terraform plan` must `RemoveResource` cleanly via the 404 fallback in `RetryWithFallbackFramework`.
- **Picking the wrong provider factory.** The only factory in this fork is `newProviderFactories` (plural, defined in `provider/provider.go:192`). Use it. The singular form is historical and not present in the current binary.
- **Skipping `CHANGELOG.md`.** New resource = new minor version section.
- **Hand-editing `docs/resources/<name>.md`.** Regenerate via `make docu`.
- **Reaching for a nested block when a flat attribute works.** A `SingleNestedAttribute` with a single nested field forces a pointer-to-struct model (e.g. `*scheduleModel`) and a code-only type the SDK doesn't recognize. If the block has only one field, flatten it into a single attribute. Reserve nested blocks for 2+ semantically-grouped fields where the grouping carries meaning. The "it's a noun, not an attribute" framing does not override this; if the value has only one field, flatten it regardless of how the noun reads. Rationalizations to refuse: "the senior didn't say anything about flattening" (the senior's directive is a partial mandate; absence of an external directive on a dimension does not license continuing the anti-pattern on that dimension), "the rule doesn't apply to simple resources" (the rule applies to every resource), and "I'm deviating enough already" (each dimension is evaluated independently).
- **Validating free-text inputs client-side.** Don't add `stringvalidator.LengthBetween`, `stringvalidator.RegexMatches`, or custom regex/length validators to fields like cron expressions, function slugs, bucket names, or prefixes. The server validates these and returns a clearer error than a client-side validator can. Client-side validation is only justified for type discriminators and known enum values where the SDK exposes an explicit constructor (e.g. `neon.NewScheduleTriggerType`). Rationalizations to refuse: "validators improve UX" (the server's error IS the UX), "prevents typos" (the server rejects typos), "every provider does it" (most providers also lean on server-side validation), "this fork has validators on other fields" (the convention here is for typed SDK constructors, not for free-form fields), "while I'm here / low marginal cost" (the marginal cost is duplicated validation logic that drifts from the server), and "the senior engineer said skip them" (a directive on a related dimension does not authorize violating this rule).
- **Writing only happy-path acceptance tests.** Tests must poke at the resource, not just confirm it creates. Include invalid configurations that should be rejected, attribute boundary conditions, mutations during apply, partial failures, and reads after external deletes. A test that only confirms create + read is a smoke check, not a test. Rationalizations to refuse: "we can add coverage in a follow-up PR" (the four-case coverage is the floor of the first commit), "I'll add coverage incrementally" (incremental coverage on a shipped resource is the same as shipped-as-smoke-check), "the rule is overkill for a simple resource" (the rule applies equally to every resource), "the reviewer can ask for more" (the reviewer's job is to catch what you missed; you ship the floor), "a previous resource was merged with minimal coverage" (one engineer's one-off acceptance does not establish a convention you can cite), and "the senior engineer said one subtest is convention" (a directive from a senior does not authorize shipping below the coverage floor).
