# Adding Neon resources and data sources

The rules behind each step are in [CONTRIBUTING.md](../../../CONTRIBUTING.md#how-changes-are-made). Read the matching
section before you start; this skill is the order of work and the checks.

## Before writing code

1. Find the Neon API operations in the [OpenAPI spec](https://neon.com/api_spec/release/v2.json) and the matching
   methods in the pinned `neon-sdk-go` version (see `go.mod`). Note each field's nullability, the error responses, and
   whether list operations paginate.
2. Decide the identity: the `id` format, the import ID, and which attributes force replacement.
3. Write down what you can't answer from the spec or the SDK, such as a field the SDK model drops. Resolve it, or
   raise it in the pull request, before building on a guess.

Don't bump the SDK in the same change. If the operation you need isn't in the pinned version, that's a separate change.

## Files, in order

| Step | File | Notes |
| --- | --- | --- |
| 1 | `provider/resource_<name>.go` or `provider/data_source_<name>.go` | Copy the structure of a recent file: `resource_snapshot.go` for a resource, `data_source_branches.go` for a paginated data source |
| 2 | `provider/provider.go` | Register the constructor in `Resources`, `DataSources`, or `EphemeralResources` |
| 3 | `provider/acc_<name>_test.go` and unit tests | See [testing.md](testing.md) |
| 4 | `examples/resources/neon_<name>/resource.tf` | Must pass `terraform validate`; unique addresses only |
| 5 | `templates/resources/<name>.md.tmpl` | Frontmatter, `{{ .Description }}`, `{{ tffile "..." }}`, `{{ .SchemaMarkdown \| trimspace }}`, and an Import section |
| 6 | `docs/` | Generated by `make docu`; never hand-written |
| 7 | `CHANGELOG.md` | An `Added` entry under `[Unreleased]` |

## Implementation checklist

- [ ] Interface assertions for every interface the type implements (`ResourceWithImportState`, `ResourceWithModifyPlan`, ...).
- [ ] Every API call goes through `projectReadiness.Retry` or `projectReadiness.Do`, with a 404 fallback in `Delete`.
- [ ] `Read` removes the resource from state on a 404.
- [ ] Computed values that are stable after create use `UseStateForUnknown`.
- [ ] Secrets are `Sensitive`. Prefer an ephemeral resource or a write-only argument over storing them.
- [ ] Data sources reuse the resource's schema through `newReadOnlyDataSourceAttrFromResourceAttr` and fetch every page.
- [ ] Writes to a parent that loses concurrent updates take a lock; see `lockNeonAuthWrites`.
- [ ] No defaults, sort orders, fallbacks, or validators the API doesn't document.
- [ ] Descriptions say what each attribute does and which ones force replacement.

## Changing an existing resource

- Changing an attribute's type or nesting: bump the schema `Version` and add an `UpgradeState` entry. For resources that
  existed in `kislerdm/neon` v0.18.0, extend `TestMigrationFromKislerdm`.
- Adding `RequiresReplace` or changing a default: plan against state written by the previous release and confirm it
  doesn't plan a replacement. The [testing-against-neon](../testing-against-neon/SKILL.md) skill shows how.
- Renaming or removing an attribute breaks every configuration that sets it. Keep the old attribute, mark it
  deprecated, and say what replaces it.

## Done

Run the checks in [AGENTS.md](../../../AGENTS.md#before-you-call-a-change-done), plus the live tests in
[testing.md](testing.md). In the pull request, show the new resource in HCL and what `terraform plan` prints for it.
